## Platform

## Users

Primary: hiring teams evaluating Ish Fuseini for product, full-stack, and applied-AI
engineering roles. They meet the app as a working artifact rather than a description —
they can start the voice agent and watch it run. Their job is to judge, in minutes,
whether Ish can design and ship a coherent applied-AI product: voice UX, real-time
observability, and product judgment in one piece.

Secondary: collaborators and prospective ishlabs clients who encounter the app as a
demonstration of what the studio can build.

## Product Purpose

A single-screen Next.js app in which an ElevenLabs voice agent conducts a
production-readiness review of a voice-agent deployment. The agent asks one question at
a time, records the evidence it hears, grades each criterion against three states, and
generates an exportable Markdown report when the conversation ends. It is a review held
as a conversation, not a checklist read aloud.

Success is a reviewer finishing a short session understanding both the deployment's
readiness and the engineering judgment that produced the tool — without the app making
any claim it cannot demonstrate.

## Positioning

The agent holds itself to the same standard it measures: the app measures its own
end-of-speech latency, tool durations, and trace events in the same panels it uses to
assess the deployment under review. Where a conventional audit produces a composite
score, this tool refuses one — findings resolve to Ready, Needs Validation, or Needs
Attention, and the report groups by state so the reader sees what to ship, verify, or
fix. It also distinguishes "could not verify" from "broken," a distinction most
checklists collapse.

## Operating Context

- Evaluated in a browser, almost always as a short walkthrough (the README carries a
  ~5-minute demo script as the canonical path through the app).
- Requires an ElevenLabs agent configured with the four client tools, referenced via
  `NEXT_PUBLIC_ELEVENLABS_AGENT_ID`; the agent ID is embedded in the client bundle at
  build time.
- Shipped as a static export (`output: "export"`) deployed to Cloudflare Pages.
- Client-side only by design: no API routes, no server, no webhooks, no persistence.
- The ElevenLabs agent's real production prompt lives in `agent/prompt.md` and is
  mirrored in the configured agent record under `agent_configs/`.

## Capabilities and Constraints

Confirmed functionality:

- Four client-side tools executed in the browser, mutating Zustand stores directly:
  `update_readiness_item`, `get_assessment_state`, `complete_assessment`, and
  `check_crm_health`.
- Three pillars and nine criteria across Latency & Turn-Taking, Tool Calling &
  Grounding, and Observability & Monitoring.
- Live session metrics (p50/p95 end-of-speech-to-first-audio latency, tool duration
  p50, tool failure count) and a timestamped trace event stream, all flowing through a
  single `emit()` seam in `stores/trace.ts`.
- Markdown report generated by a pure function (`lib/report.ts`) and exported by
  download.

Constraints and deliberate cuts:

- No backend, no persistence, no multi-session state, no router, no PDF export.
- `check_crm_health` always times out after 5 seconds — an intentional, controlled
  failure path, not a bug. The agent must mark it Needs Validation, not Needs Attention.
- No composite score, percentage, rating, or grade anywhere; this is enforced by tests
  (`__tests__/e2e-flow.test.ts`).
- Tool handlers are the only writers to state; UI components read from stores.
- `check_crm_health` is a simulated dependency check; no real CRM integration exists.
- State is lost on refresh (acceptable for v1).

## Product Principles

1. **The agent holds itself to the standard it measures.** Self-measurement is the
   proof; the tool evaluates itself with the same criteria and panels it applies to the
   deployment under review.
2. **Conversation over checklist.** One question at a time, with contextual follow-ups;
   the discovery is the product.
3. **Three states, never a score.** Map findings to action — ship it, verify it, fix it —
   and refuse the false precision of a composite percentage.
4. **Unverified is not broken.** Separate "could not check" from "is broken," and make
   that distinction visible in both the conversation and the report.
5. **Never fabricate.** Record only what the user actually said, and make no claim the
   app cannot demonstrate.

## Accessibility & Inclusion

The design system requires accessible contrast (4.5:1 for normal text, 3:1 for large
text and meaningful UI indicators) and prohibits communicating a state by color alone —
readiness statuses pair an icon and a text label with their color. These requirements
are inherited from `docs/DESIGN.md` and must hold for any new surface.
